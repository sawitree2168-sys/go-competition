# GO TOURNAMENT — Source Data Architecture

สถานะ: แบบร่างพร้อมเชื่อม Supabase (ยังไม่ใช่ข้อมูลจริง)

## เป้าหมาย

สร้างแหล่งข้อมูลกลางแบบเดียวกับหน้าสาธารณะของ Thailand Go Super Series โดย GO TOURNAMENT เพิ่มข้อมูลระดับคิว ประวัติการแข่งขัน รายละเอียดสถาบัน และการแยกสิทธิ์ผู้จัดงานอย่างชัดเจน

หน้าโปรไฟล์นักกีฬาใช้ URL เต็ม เช่น `/athletes/GT-0001` ไม่เปิดเป็นป๊อปอัป

## ขอบเขต GO TOURNAMENT และ Thailand Go Super Series

- GO TOURNAMENT รับและแสดงงานแข่งขันทั่วไปทุกระดับ
- สถิติการแข่งขัน เช่น จำนวนงาน จำนวนครั้งที่เข้าร่วม ผลงาน และอันดับ แยกดูเป็นรายปี
- คะแนนสะสมระดับคิวเป็นบัญชีต่อเนื่องของนักกีฬา ไม่รีเซ็ตเมื่อขึ้นปีใหม่
- GO TOURNAMENT ไม่คำนวณคะแนนระดับดั้ง เพราะใช้ GAT POINT เป็นระบบหลักอยู่แล้ว
- งานที่จะสมัครเข้าร่วม Thailand Go Super Series ต้องมีอย่างน้อยหนึ่งรุ่นประเภท `HIGH_DAN` หรือ `OPEN_DAN`
- การมีรุ่นดั้งทั่วไปอย่างเดียวไม่ทำให้งานผ่านเงื่อนไข Super Series
- ผู้ดูแล Super Series ต้องตรวจรุ่นที่ใช้ยืนยันก่อนอนุมัติงานเข้าสู่ฤดูกาล

## แหล่งข้อมูลหลัก

| สิ่งที่หน้าเว็บแสดง | ตารางต้นทาง | เผยแพร่สาธารณะ |
|---|---|---|
| โปรไฟล์นักกีฬา | `athlete_public_profiles` | เฉพาะแถวที่ `is_published = true` |
| สถาบัน | `institutions` | ได้ |
| รายการแข่งขัน | `events` | เฉพาะงานที่เผยแพร่ และแยกตามปีแข่งขัน |
| ฤดูกาล/สมาชิก Super Series | `competition_series` + `series_seasons` + `series_event_memberships` | เฉพาะงานที่อนุมัติ |
| รุ่นแข่งขัน | `divisions` | ตามสถานะของงาน |
| ประวัติลงแข่งขัน | `registrations` + `event_results` | เฉพาะผลที่ประกาศแล้ว |
| ผลรายรอบ | `matches` | เฉพาะรอบที่ประกาศแล้ว |
| คะแนนคิว | `kyu_rating_accounts` + `kyu_rating_ledger` | เฉพาะรายการที่ผ่านการคำนวณและเผยแพร่ |
| คะแนนระดับดั้ง | แหล่ง GAT POINT ภายนอก | แสดงผลเท่านั้น ไม่คำนวณในระบบนี้ |
| รูปนักกีฬา | Supabase Storage + `athlete_photos` | เฉพาะรูปที่อนุมัติ |

ข้อมูลส่วนตัว เช่น วันเกิด เบอร์โทร อีเมล เอกสารยืนยัน และหมายเหตุของผู้จัด ต้องไม่อยู่ในตารางสาธารณะ

## ความสัมพันธ์ของข้อมูล

- นักกีฬาหนึ่งคนมีโปรไฟล์สาธารณะหนึ่งรายการ และลงแข่งขันได้หลายงาน
- งานหนึ่งงานมีหลายรุ่น หลายรอบ หลายคู่แข่งขัน และหลายผลสรุป
- งานหนึ่งงานเข้าร่วม Super Series ได้เมื่อมีรุ่น `HIGH_DAN` หรือ `OPEN_DAN` ที่ใช้ยืนยัน
- หน้าสถิติกรองตาม `competition_year` แต่บัญชี `kyu_rating_accounts` และ ledger ไม่ผูกกับปี
- สถาบันหนึ่งแห่งมีนักกีฬาได้หลายคน
- คะแนนคิวทุกการเปลี่ยนแปลงเก็บเป็น ledger ห้ามแก้ยอดรวมโดยไม่มีรายการอ้างอิง
- ผลย้อนหลังที่เข้ามาทีหลังสร้าง revision แล้วคำนวณใหม่ตามลำดับเวลา

## การอ่านข้อมูลเพื่อให้เว็บเร็ว

1. หน้างานเขียนผลลงตารางธุรกรรมครั้งเดียว
2. เมื่อผู้จัดกด Finalize ระบบสร้างผลสรุปที่เผยแพร่ได้
3. หน้าสาธารณะอ่านเฉพาะข้อมูล published และ index แล้ว
4. ใช้ cache/revalidation ที่หน้าเว็บ ไม่สแกน Google Sheet ทุกครั้ง
5. การส่งผลย้อนหลังเข้าคิว recalculation และเผยแพร่ revision ใหม่เมื่อเสร็จ

## สิทธิ์

- Public: อ่านเฉพาะข้อมูลที่เผยแพร่แล้ว
- Athlete/Guardian: แก้รูปของบัญชีตนเองและดูข้อมูลที่ได้รับสิทธิ์
- Institute: ดูภาพรวมลูกศิษย์ที่เชื่อมกับสถาบันตามสิทธิ์
- Organizer: จัดการเฉพาะงานที่ตนเป็นเจ้าของหรือได้รับมอบหมาย
- Admin: ตรวจรูป แก้ข้อมูลอ้างอิง และจัดการข้อพิพาท

ทุกตารางใน schema `public` ต้องเปิด RLS และห้ามนำ service-role key ไปไว้ใน browser

## ลำดับเชื่อมต่อ

1. เปิดใช้งานโปรเจกต์ Supabase `go-competition`
2. ตรวจและใช้ไฟล์ `supabase/schema/go_tournament_source.sql`
3. สร้าง bucket รูปนักกีฬาแบบ private และเส้นทางอนุมัติรูป
4. ย้าย fixture จาก `lib/athletes.ts` เข้าฐานข้อมูลทดสอบ
5. เปลี่ยนหน้าค้นหา/โปรไฟล์ให้ query ผ่าน data-access layer
6. ทดสอบ RLS: คนทั่วไป, นักกีฬา, ผู้จัดงานอื่น และเจ้าของงาน
7. เชื่อม Vercel environment variables แล้วทดสอบ preview
